# ADR-0010: Drizzle for data access and migrations

- **Status:** Accepted
- **Date:** 2026-11-21
- **Category:** Data

## Context

The database is PostgreSQL ([ADR-0005](0005-use-postgresql.md)) and the backend is TypeScript with a hexagonal architecture ([ADR-0003](0003-backend-hono-modular-monolith.md)): only infrastructure adapters talk to the database, behind ports defined by the domain.

The backend needs:

- **Typed queries**, so a change in the schema breaks the build instead of failing at runtime.
- **Full use of PostgreSQL:** aggregations, window functions, `FILTER`, extensions. The heavy work of the application lives in these queries, so the tool must not hide SQL.
- **Reproducible migrations**, versioned with the code and applied automatically before the backend starts, locally and in deployment ([ADR-0008](0008-infrastructure-docker-compose-and-k3s.md)).
- **A small runtime**, since the backend is bundled into a single file for its image.

## Decision

Data access and migrations use **[Drizzle ORM](https://orm.drizzle.team/)** with **drizzle-kit**, on the `pg` driver.

### Schema and queries

- The schema is written in TypeScript, **in the module that owns the tables** (`<module>/infrastructure/repository/postgres/schema.ts`), next to the repository adapters that use it. Drizzle infers the row types from it.
- Queries use Drizzle's SQL-like builder. Where it falls short (complex aggregations), the `sql` template is used, still typed and parameterised.
- **Only repository adapters in `infrastructure/` import Drizzle.** Domain and application code depend on ports, never on Drizzle types.
- **Read queries can join tables owned by another module**, when the aggregation needs their data (for example grouping monthly metrics by an attribute of the advisory firm). The join is written in the repository adapter of the module that runs the query, which imports only the other module's `schema.ts`. Writes stay in the module that owns the table. A single join in the database is far cheaper than fetching the related data through a port and combining it in the application.
- The database client and connection pool are shared technical infrastructure (`shared/infrastructure/database`), created once in the composition root.

### Migrations

- Migrations are **plain SQL files generated by drizzle-kit** from the schema, reviewed and committed to the repository. Changes that drizzle-kit cannot express (for example creating extensions) are written as custom SQL migrations.
- Migrations are **never generated at runtime**. They are applied by a dedicated entry point of the backend, which runs as a one-off task before the backend starts: a one-off service in Docker Compose and a Job in Kubernetes.
- Applied migrations are tracked in the database, so running the task again is safe.

## Alternatives considered

- **Prisma:** a mature ORM with a good developer experience, but its own schema language and query engine add a separate layer between the code and PostgreSQL, and aggregations end up in raw SQL anyway. Its client is heavier to bundle.
- **Kysely:** an excellent typed query builder, but schema and migrations have to be maintained separately from the types.
- **Raw SQL with a driver only:** maximum control, but no typing of results and hand-written migrations tooling.
- **TypeORM / MikroORM:** decorator-based entities that push persistence concerns into the domain model, against the hexagonal architecture.

## Consequences

### Positive

- Queries and results are typed from a single schema definition.
- SQL stays visible: complex aggregations can be written in the database's own terms.
- Migrations are reviewable SQL files in the repository, applied the same way in every environment.
- A small runtime that bundles into the backend image.

### Negative

- Drizzle is younger than Prisma, and some advanced features require falling back to `sql`.
- Generated migrations must be reviewed: drizzle-kit can propose destructive changes (for example a column rename seen as drop and add).
- The schema lives in each module, but read queries join across modules: a module that reads another module's tables depends on their schema, and a change to those tables can break it. The integration tests of the repository adapters catch it.
