# ADR-0006: Quality and observability with SonarQube Cloud and Sentry

- **Status:** Accepted
- **Date:** 2026-11-20
- **Category:** Quality

## Context

The product is built in vertical slices and released continuously from the start. With frequent releases, two kinds of feedback are needed:

- **Before release:** whether the code that is about to be merged is maintainable, tested and free of obvious bugs and security issues.
- **After release:** whether something breaks in production, and where.

There is also the question of how users behave in the product. The user is an internal manager who is in direct contact with the team. That person can tell the team, first hand, what works, what is missing and what they need.

The tools should be free for a project of this size and integrate with GitHub and the existing CI.

## Decision

### Code quality: SonarQube Cloud

**SonarQube Cloud** analyses the repository on every pull request and on the main branch, from GitHub Actions.

- It reports bugs, code smells, duplication and security hotspots, and comments on the pull request.
- It reads the test coverage produced by Vitest (`lcov`) for the whole monorepo.
- A **quality gate** on new code (coverage, duplication, no new bugs or vulnerabilities) must pass before merging.
- It complements, and does not replace, ESLint and the TypeScript compiler, which still run in CI.
- **One SonarQube Cloud project for the whole monorepo:** one analysis, one quality gate and combined coverage, with the same rules for every package. A package is split into its own project only if it needs a different quality gate (for example, the design system if it is consumed by other products).

### Error monitoring: Sentry

**Sentry** captures runtime errors in both the backend and the frontend.

- **One Sentry project per application** (backend and frontend), in the same organisation. They are different platforms, with different SDKs, source maps and kinds of errors, so separate projects keep alerts and noise apart. Both share the same release version, and distributed tracing links a frontend request to its backend trace across projects.

- Backend: the Node.js SDK, integrated with the HTTP framework's error handling.
- Frontend: the React SDK, with an error boundary and source maps uploaded from CI, so stack traces point to the original TypeScript.
- Every event is tagged with the **release version** generated by the release process ([ADR-0001](0001-use-conventional-commits.md)) and with the environment, so an error can be traced to the release that introduced it.
- **No personal data is sent** (`sendDefaultPii` disabled), and business data is not attached to events.
- The DSN and auth tokens are configuration, never committed to the repository.

### No behaviour analytics for now

No product-analytics or session-recording tool (such as PostHog or Microsoft Clarity) is added. The user is a manager in direct contact with the team, and their direct feedback is richer and more valuable than usage statistics from a single user. This decision will be revisited if the number of users grows.

## Alternatives considered

- **Self-hosted SonarQube or Sentry:** they remove the dependency on an external service, but add infrastructure to run and maintain. Not justified at this size.
- **ESLint and TypeScript only:** necessary, but they give no coverage tracking, duplication analysis or quality gate on pull requests.
- **Logs only, without error monitoring:** errors would be found only when someone reports them or reads the logs, with no grouping, alerts or release tracking.
- **PostHog, Microsoft Clarity or Google Analytics:** useful with many users. With one internal user who talks to the team directly, they add a dependency and privacy concerns (session recordings showing business data) without adding information.

## Consequences

### Positive

- Every pull request gets an objective quality check before merging.
- Production errors are detected, grouped and linked to the release that introduced them, which fits continuous release.
- Both tools are free at this scale and integrate with GitHub.
- User feedback comes directly from the user, without tracking.

### Negative

- Dependency on two external SaaS services and their free-plan limits, which can change.
- Secrets (Sonar token, Sentry DSN and auth token) must be managed in CI and in each environment.
- Without analytics, the team has no quantitative data on usage. This relies on keeping regular contact with the user.
